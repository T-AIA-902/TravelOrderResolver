1. Introduction et contexte du projet

1.1 Enonce du probleme

Le projet Travel Order Resolver consiste a concevoir un programme capable de traiter des commandes textuelles en langage naturel pour generer un itineraire ferroviaire adapte. Le logiciel recoit des ordres de voyage sous forme de texte (par exemple provenant d'un chatbot), et produit au minimum une ligne de train correspondant aux attentes du client, en s'appuyant sur les horaires SNCF francais.

Le systeme doit distinguer les ordres valides des ordres invalides, identifier le depart et la destination (qui peuvent etre une gare ou une ville), puis fournir un itineraire ferroviaire correspondant. Le programme NLP doit gerer les phrases en francais ; a titre de bonus, il peut egalement gerer d'autres langues.

1.2 Pipeline global

Le systeme s'articule autour de trois composants majeurs :

Speech-to-Text (optionnel) NLP Pipeline Recherche d'itineraire ┌────────────────┐ ┌───────────────────┐ ┌─────────────────────┐ │ Audio (WAV) │────────>│ Extraction de │──────>│ Graphe ferroviaire │ │ Whisper │ │ gares (NER) │ │ Dijkstra / A* │ └────────────────┘ └───────────────────┘ └─────────────────────┘

1.3 Format d'entree/sortie

Le composant NLP lit des phrases au format sentenceID,sentence (une par ligne, encodage UTF-8) et produit :

  • Pour une commande valide : sentenceID,Depart,Destination
  • Pour une commande invalide : sentenceID,Code (ou Code peut etre INVALID, NOT_TRIP, UNKNOWN, etc.)

Le composant de recherche d'itineraire recoit un triplet sentenceID,Depart,Destination et retourne une sequence de villes : sentenceID,Depart,Etape1,Etape2,...,Destination.

2. Architecture complete du systeme

2.1 Vue d'ensemble du pipeline NLP

L'architecture suit un patron modulaire ou chaque couche est definie par une classe abstraite (ABC) dans src/nlp/interfaces.py, permettant de brancher differentes implementations (Regex, SpaCy, CamemBERT, Flan-T5) sans modifier le pipeline.

Texte brut | v [PRE-TRAITEMENT] STTArtifactFilter + Preprocessor | v [DETECTION DE LANGUE] RegexLanguageDetector | LangdetectLanguageDetector | -> (code_langue, confiance) v [CLASSIFICATION D'INTENTION] RegexIntentClassifier | SpacyIntentClassifier | | CamembertIntentClassifier | FlanT5IntentClassifier | -> (TRIP | NOT_TRIP | UNKNOWN, confiance) v [EXTRACTION D'ENTITES] RegexEntityExtractor | SpacyEntityExtractor | | CamembertEntityExtractor | FlanT5EntityExtractor | -> {departure, destination, intermediate[]} v [POST-TRAITEMENT] FuzzyPostProcessor (RapidFuzz -> noms SNCF officiels) | v PredictionResult | v [RECHERCHE D'ITINERAIRE] Dijkstra | A* | MOA* (si TRIP valide) | v Itineraire final

Le fichier src/nlp/types.py definit les structures de donnees centrales :

2.4 Couche de pre-traitement

2.4.1 STTArtifactFilter (src/nlp/pre/stt_filter.py)

Ce filtre supprime les artefacts produits par les systemes de transcription vocale (Whisper notamment). Il reconnait plus de 70 marqueurs de bruit :

  • Marqueurs entre crochets : [coupure], [bruit], [musique], [silence], [inaudible]
  • Marqueurs entre asterisques : *bruit*, *rire*
  • Motifs regex : contenu entre crochets, entre asterisques, points de suspension multiples, tirets repetes

La methode filter(text) retourne un tuple (texte_nettoye, est_bruit_pur). Si le texte entier est du bruit, la phrase est classee UNKNOWN sans traitement supplementaire.

2.4.2 Preprocessor (src/nlp/pre/preprocessor.py)

Le preprocesseur applique une serie de normalisations configurables via PreprocessorConfig :

ParametreDefautDescription
lowercaseFalseMise en minuscules (desactive pour preserver la detection de langue)
remove_accentsFalseSuppression des accents (desactive pour le francais)
normalize_whitespaceTrueTabulations et retours a la ligne convertis en espaces
normalize_apostrophesTrue6 variantes d'apostrophe normalisees vers ' standard
normalize_hyphensTrue6 variantes de tiret normalisees vers - standard

L'ordre d'application est : normalisation Unicode (NFC) → apostrophes → tirets → accents → minuscules → ponctuation → espaces → strip.

2.5 Couche de detection de langue

2.5.1 RegexLanguageDetector

Detecteur a base de regles utilisant environ 25 motifs regex pour le francais (ex. je veux, aller a, prendre le train) et 22 pour l'anglais (ex. I want to, from X to Y). Le score est calcule par le ratio de correspondances trouvees. Des indicateurs espagnols, allemands et italiens permettent de detecter les langues tierces.

Performance : 67,5 % de precision sur le jeu de test.

2.5.2 LangdetectLanguageDetector

Encapsule la bibliotheque langdetect (basee sur des n-grammes statistiques). Mappe les codes ISO vers les categories internes : fr → FRENCH, en → ENGLISH, tout autre → UNKNOWN. La graine est fixee a 0 pour la reproductibilite.

Performance : 77,9 % de precision sur le jeu de test (+10,4 % par rapport au Regex).

2.6 Couche de classification d'intention

2.6.1 RegexIntentClassifier

Plus de 50 motifs regex couvrant le francais, l'anglais, l'espagnol, l'allemand et l'italien. Si un motif de voyage est detecte, retourne TRIP avec confiance 0,8. Si le texte contient 2 a 4 mots sans motif reconnu, retourne TRIP avec confiance 0,5 (potentiellement des noms de gares). Sinon, retourne NOT_TRIP.

Performance (zero-shot) : 65,8 % de precision sur le jeu de test.

2.6.2 SpacyIntentClassifier

Heuristique basee sur le modele NER fr_core_news_lg de SpaCy : la presence d'entites LOC/GPE indique une intention de voyage. La confiance augmente avec le nombre d'entites detectees (min 0,5, max 0,8).

Performance (zero-shot) : 79,1 % de precision sur le jeu de test.

2.6.3 CamembertIntentClassifier

Classification zero-shot avec le modele almanach/camembert-base via un pipeline HuggingFace. Les hypotheses candidates sont : « demande de voyage en train » et « autre question ».

Performance (zero-shot) : 32,4 % de precision sur le jeu de test.

2.6.4 CamemBERT fine-tune pour la classification

Architecture CamembertForSequenceClassification avec 3 classes (TRIP, NOT_TRIP, UNKNOWN), fine-tunee sur le dataset augmente (70k entrainement, 15k validation). Voir la section 6 pour les resultats detailles.

Performance (fine-tune) : 99,95 % de precision sur le jeu de test.

2.7 Couche d'extraction d'entites

2.7.1 RegexEntityExtractor

Motifs regex pour le francais et l'anglais, appliques dans un ordre de priorite :

  1. X puis Y puis Z (3 gares francais)
  2. de/depuis X vers/a/direction Y
  3. a Y depuis/en partant de X
  4. X vers/direction Y
  5. from X to/towards Y (anglais)
  6. Repli : detection de gares potentielles par elimination des mots-outils (200+ mots-outils francais et anglais)

Performance (sans fuzzy) : 33,3 % de precision ; avec fuzzy : 57,1 %.

2.7.2 SpacyEntityExtractor

Utilise les entites LOC/GPE extraites par fr_core_news_lg. La premiere entite est affectee au depart, la derniere a la destination. Les entites apparaissant apres des mots-cles intermediaires (via, en passant par) sont marquees comme etapes.

Performance (sans fuzzy) : 27,8 % ; avec fuzzy : 34,2 %.

2.7.3 CamembertEntityExtractor (zero-shot)

Utilise le modele almanach/camembert-base pour calculer des embeddings de phrases, puis effectue un matching exact (par sous-chaine) contre la base de donnees de gares SNCF. Le matching par similarite d'embeddings a ete desactive en raison d'un taux eleve de faux positifs.

Performance (sans fuzzy) : 16,3 % ; avec fuzzy : 31,2 %.

2.7.4 CamemBERT fine-tune pour le NER

Architecture CamembertForTokenClassification avec 7 labels BIO : O, B-DEP, I-DEP, B-DEST, I-DEST, B-INTER, I-INTER. Fine-tune sur 51 800 phrases TRIP du dataset augmente. Voir la section 6 pour les resultats detailles.

Performance (fine-tune) : F1 = 98,45 %, Precision = 98,33 %, Rappel = 98,58 %.

2.8 Couche de post-traitement

2.8.1 StationMatcher (src/nlp/post/station_matcher.py)

Matching fuzzy base sur RapidFuzz (algorithme de Levenshtein optimise). L'algorithme fonctionne en plusieurs etapes :

  1. Verification du cache (acceleration massive pour les requetes repetees)
  2. Matching exact par prefixe avec l'index pre-calcule first_words
  3. Matching fuzzy sur les premiers mots (bonus de +20 points)
  4. Matching fuzzy sur les noms complets (scorer WRatio)
  5. Selection du meilleur resultat si le score depasse le seuil (defaut : 80)

2.8.2 FuzzyPostProcessor

Adaptateur du pipeline qui applique le StationMatcher au depart, a la destination et a chaque etape intermediaire. Apporte une amelioration moyenne de +15 % sur la precision d'extraction.

2.9 Orchestration du pipeline

La classe NLPPipeline (src/nlp/pipeline.py) compose les differentes couches par injection de dependances :

pipeline = NLPPipeline(
    language_detector=LangdetectLanguageDetector(),
    intent_classifier=SpacyIntentClassifier(),
    entity_extractor=RegexEntityExtractor(),
    config=PipelineConfig(use_station_matching=True)
)

La methode process(text) enchaine : pre-traitement → detection de langue → classification d'intention → extraction d'entites → matching de gares → validation (si TRIP mais aucune gare trouvee, degradation vers NOT_TRIP).

2.10 Moteur de recherche d'itineraire

2.10.1 Construction du graphe

Le graphe ferroviaire est construit a partir de trois fichiers SNCF open data :

FichierContenuTaille
gares-de-voyageurs.json6 101 gares avec coordonnees GPS579 Ko
liste-des-gares.jsonMapping gares-lignes avec points kilometriques4,9 Mo
lignes-par-type.jsonLignes ferroviaires avec geometrie9,4 Mo

Le graphe est un MultiGraph NetworkX (aretes multiples entre memes noeuds). Les noeuds representent les gares avec leurs coordonnees GPS. Les aretes sont de type TRAIN (connexions ferroviaires) ou WALK (correspondances pietonnes dans les grands hubs urbains, rayon 8 km). Les poids des aretes LGV sont divises par 3 pour refleter la vitesse reelle (280 km/h contre 80 km/h).

2.10.2 Algorithme de Dijkstra

Implementation classique avec file de priorite binaire (heapq). Complexite : O((V + E) log V). Garantit le chemin optimal a objectif unique (distance ponderee minimale).

2.10.3 Algorithme A*

Heuristique admissible : h(n) = distance_geodesique(n, but) / 3. La division par 3 correspond au meilleur cas (LGV en ligne droite), garantissant l'admissibilite. En pratique, A* explore 50 a 70 % de noeuds en moins que Dijkstra pour un resultat identique.

2.10.4 Algorithme MOA* (Multi-Objective A*)

Recherche de routes Pareto-optimales selon trois objectifs simultanees :

  1. Temps (heures) : dist_km / vitesse
  2. Distance (km) : distance totale
  3. Correspondances : nombre de changements de ligne

L'algorithme maintient une frontiere de Pareto par noeud et retourne jusqu'a 3 itineraires non-domines. Complexite : O(k × (V + E) log V) ou k est le nombre de solutions Pareto.

3. Processus d'entrainement et jeux de donnees

3.1 Generation du jeu de donnees

Aucun jeu de donnees existant ne correspondant au probleme specifique de commandes de voyage ferroviaire en francais, nous avons genere un corpus synthetique de 100 000 phrases a l'aide du script datasets/scripts/generate_base.py.

3.1.1 Methodologie de generation

La generation repose sur plus de 200 gabarits de phrases par categorie, couvrant une grande diversite de structures grammaticales :

  • Phrases formelles : « Je souhaite me rendre de {depart} a {destination} »
  • Phrases informelles : « Faut que j'aille a {destination} depuis {depart} »
  • Hesitations : « Euh ben train {depart} {destination} »
  • Patterns minimaux : « {depart} {destination} », « Vers {destination} »
  • Gabarits multilingues : anglais (10 gabarits), espagnol, allemand, italien (5 chacun)
  • Etapes intermediaires (15 % des TRIP) : « en passant par », « via », « puis... puis »

3.4.3 Alignement des sous-tokens

CamemBERT utilise un tokenizer SentencePiece qui decoupe les mots en sous-tokens. L'alignement des labels est crucial :

  • Tokens speciaux (<s>, </s>, <pad>) : label = -100 (ignore dans le calcul de la perte)
  • Premier sous-token d'un mot : recoit le label du mot
  • Sous-tokens suivants du meme mot : label = -100 (ignore)

Cette strategie evite que les sous-tokens arbitraires influencent l'entrainement tout en preservant les labels au niveau des mots.

3.4.4 Conversion a la volee

Le dataset augmente (format CSV) est converti a la volee en annotations NER par la fonction convert_augmented_sample(). Pour chaque phrase TRIP, les noms de gares de la verite terrain sont recherches dans les tokens par matching normalise (minuscules, sans tirets ni apostrophes). Les labels B-DEP/I-DEP et B-DEST/I-DEST sont assignes aux tokens correspondants.

5. Exemple detaille de traitement d'une phrase

5.1 Exemple 1 : Commande de voyage valide

Phrase d'entree : « Je voudrais aller de Paris a Lyon en passant par Dijon »

Etape 1 : STTArtifactFilter
Aucun artefact detecte ([...], *...*, etc.). Le texte passe tel quel.
Sortie : "Je voudrais aller de Paris a Lyon en passant par Dijon" — est_bruit = False
Etape 2 : Preprocessor
Normalisation Unicode (NFC), normalisation des apostrophes et tirets. Le texte ne contient ni apostrophes speciales ni tirets a normaliser. Les espaces sont deja normaux.
Sortie : "Je voudrais aller de Paris a Lyon en passant par Dijon" (inchange)
Etape 3 : Detection de langue (Langdetect)
La bibliotheque langdetect analyse les n-grammes et detecte le francais avec haute confiance.
Sortie : ("FRENCH", 0.9999)
Etape 4 : Classification d'intention (SpaCy)
Le modele SpaCy NER detecte 3 entites de type LOC/GPE : « Paris », « Lyon », « Dijon ». Confiance = min(0.5 + 3 × 0.1, 0.8) = 0.8.
Sortie : ("TRIP", 0.8)
Etape 5 : Extraction d'entites (Regex)
Le motif de/depuis X vers/a Y capture : depart = « Paris », destination = « Lyon ».
Le motif en passant par X capture l'intermediaire : « Dijon ».
Sortie : {"departure": "Paris", "destination": "Lyon", "intermediate": ["Dijon"]}
Etape 6 : Post-traitement fuzzy
StationMatcher verifie chaque nom contre la base SNCF (6 101 gares) :
• « Paris » → correspondance exacte → « Paris » (score 100)
• « Lyon » → correspondance exacte → « Lyon » (score 100)
• « Dijon » → correspondance exacte → « Dijon » (score 100)
Sortie : entites inchangees (noms deja corrects)
Etape 7 : Construction du PredictionResult
PredictionResult(
  intent=TRIP, intent_confidence=0.8,
  language=FRENCH, language_confidence=0.9999,
  departure="Paris", destination="Lyon",
  intermediates=["Dijon"],
  is_valid_trip=True,
  model_name="pipeline(Regex)"
)
Etape 8 : Recherche d'itineraire (A*)
Le graphe SNCF est interroge avec A* pour Paris → Dijon, puis Dijon → Lyon.
L'heuristique geodesique / 3 guide la recherche vers les LGV.
Sortie : 1,Paris,Dijon,Lyon

5.2 Exemple 2 : Phrase avec erreurs STT

Phrase d'entree : « euh ben [bruit] de monparnasse a lion svp »

Etape 1 : STTArtifactFilter
Le marqueur [bruit] est supprime.
Sortie : "euh ben de monparnasse a lion svp"
Etape 2 : Preprocessor
Normalisation des espaces (doubles espaces collapses).
Sortie : "euh ben de monparnasse a lion svp"
Etape 3 : Detection de langue
("FRENCH", 0.85) — « de », « a », « svp » sont des indicateurs francais.
Etape 4 : Classification d'intention
("TRIP", 0.8) — le mot « de... a » declenche le motif de voyage.
Etape 5 : Extraction d'entites
Le motif de X a Y capture : depart = « monparnasse », destination = « lion svp ».
Apres nettoyage des mots temporels (« svp » supprime) : destination = « lion ».
Etape 6 : Post-traitement fuzzy
• « monparnasse » → fuzzy match → « Paris Montparnasse » (score 88)
• « lion » → fuzzy match → « Lyon » (score 86)
Le matching corrige les fautes d'orthographe et les noms informels.
Sortie finale
2,Paris Montparnasse,Lyon

Phrase d'entree : « Quel temps fait-il demain a Paris ? »

Traitement
• Langue : FRENCH (confiance 0,95)
• Intention : NOT_TRIP (aucun motif de voyage detecte malgre la presence de « Paris »)

7.1 Module d'evaluation

  metrics.py          # Dataclasses : IntentResults, EntityResults, etc.
  reporting.py        # Affichage de tables et export JSON

  evaluators/
    intent.py         # Evaluateur de classification d'intention
    entity.py         # Evaluateur d'extraction d'entites
    language.py       # Evaluateur de detection de langue
    combined.py       # Evaluateur de combinaisons pipeline

7.2 Metriques utilisees

Les metriques principales sont calculees pour chaque classe :

MetriqueFormuleInterpretation
PrecisionTP / (TP + FP)Proportion de predictions positives correctes
RappelTP / (TP + FN)Proportion d'echantillons positifs correctement identifies
F1-Score2 × (P × R) / (P + R)Moyenne harmonique de la precision et du rappel
Precision globaleCorrects / TotalTaux de predictions correctes
Macro F1Moyenne des F1 par classePerformance equilibree entre les classes
LatenceTemps moyen par echantillon (ms)Performance en temps reel

Pour le NER, les metriques sont calculees avec seqeval qui utilise l'evaluation au niveau entite (un B-DEP suivi de I-DEP forme une seule entite evaluee).

9. Fonctionnalites bonus

Algorithme A* multi-objectif produisant jusqu'a 3 itineraires Pareto-optimaux equilibrant temps, distance et nombre de correspondances. Visualisation interactive avec Folium/Leaflet.

Integration de CodeCarbon pour estimer les emissions de CO2 de chaque requete et de l'entrainement. Prise en compte du mix energetique francais.

Module src/visualization/map_visualizer.py generant des cartes interactives HTML avec Folium. Affichage des itineraires avec segments colores par type de ligne (LGV, TER), correspondances pietonnes en pointilles, legende interactive.

9.7 Support multilingue

Support complet des etapes intermediaires (« en passant par », « via »). Les entites intermediaires sont extraites au niveau NER (labels B-INTER/I-INTER) et utilisees par le moteur de recherche d'itineraire pour generer des routes multi-segments.

11. Conclusion

Le projet Travel Order Resolver demontre une approche methodique du traitement du langage naturel applique aux commandes de voyage ferroviaire. La strategie adoptee suit les recommandations du sujet : securiser une premiere livraison avec des solutions simples (Regex), mesurer la qualite avec des metriques rigoureuses, puis ameliorer progressivement avec des modeles plus complexes (SpaCy, CamemBERT).

Les resultats principaux sont :

  • Approches sans fine-tuning : le meilleur pipeline combine SpaCy pour l'intention (79,1 %) et Regex + Fuzzy pour les entites (57,1 %), avec une latence de ~17 ms par echantillon.
  • Apres fine-tuning : CamemBERT fine-tune sur notre dataset de 100 000 phrases atteint 99,95 % en classification d'intention et 98,45 % en F1 pour l'extraction d'entites, surpassant massivement toutes les autres approches.
  • Post-traitement fuzzy : composante la plus impactante parmi les ameliorations non-ML (+15 % en moyenne, +23,7 % pour le Regex).
  • Dataset synthetique realiste : les 14 types d'erreurs STT simulees et l'architecture a deux niveaux (base/augmente) permettent une evaluation rigoureuse de la robustesse des modeles.

Le systeme est complete par un moteur de recherche d'itineraire (Dijkstra, A*, MOA*), une transcription vocale (Whisper), un monitoring d'infrastructure, et une interface web, demontrant une integration de bout en bout.
